# 12 · 读者契约 v4（定稿）

> 依据：`docs/11-契约对读者级的影响.md`（A–E 五组对照，共 400 次真实调用；全部缓存可复现）。
> 状态：**定稿**，作为"读者如何读记忆"的规范；改动必须重跑同一套对照。

## 1. 为什么需要契约

检索已经不是瓶颈：证据级 R@4 ≈ 0.97、R@20 = 1.0，34/36 题的证据全在前 4 条。
瓶颈在**读者怎么处理多条记录**——尤其"说法冲突"和"没有日期"。

实测（40 题，可答 36）：

| 组 | 契约 | ✅ | ❌ | 合格率 | 可答题正确率 |
|---|---|---:|---:|---:|---:|
| A | 题库原说明（无契约） | 26 | 11 | 72.5% | 61.1% |
| B | v2 | 19 | 1 | 97.5% | 41.7% |
| C | v2 + 日期前缀 | 20 | 0 | 100% | 44.4% |
| D | v3 | 28 | 7 | 82.5% | 66.7% |
| **E** | **v4** | **26** | **2** | **95.0%** | **61.1%** |

- v2 把"自信答错"几乎清零，但把 7 道本该答对的题变成"反问"——它没有区分"会变的属性"和"稳定事实"。
- v3 修好了那 7 题（A→D：4 好 0 坏），但"以最新为准"边界过宽，同日冲突/跨场景记录被强行排序，❌ 回到 7。
- v4 加了三条硬规则（同日不可排序、稳定事实永不挑边、无日期≠更旧 + 计数题规则），**同时压住两头**：✅ 不低于基线、❌ 从 11 降到 2。

## 2. 契约全文（v4，逐字）

```
回答这些关于我本人记忆的问题时，请遵守：
1. 直接给出答案；如果答案来自记忆，说明依据的是哪一天记的那条。
2. 如果多条记录对同一件事给了不同的说法，按下面处理：
   a. 只有当两条记录的日期不同、并且较晚的那条明确写明了发生了改变
      （换了、改成、调到、搬到、减到、换成、不再 等），才以较晚的那条为准直接回答，
      并说明"按 X 年 X 月 X 日的记录"；旧说法最多用一句话带过。
   b. 如果日期相同、或者较晚的记录没有明确说明发生了改变（只是补记、换个说法），
      就认为无法确定哪条对，把每种说法和日期列出来，然后问我。
   c. 不会随时间变化的事实（血型、过敏、出生年份、药量、宠物的年龄）永远按 b 处理，
      即使日期不同也不要自己挑一条。
   例外：如果其中某条是「已确认」「已作废」这种我本人裁决过的结论，以那条为准直接回答。
3. 如果记忆里根本没有答案，直接说没有，不要编。
4. 如果所有记录说法一致，直接回答，不要把同一件事换个说法重复一遍。
5. 如果有关记录没有日期，说明"这条没记时间"，给出更可能的那一条作为倾向，
   但不要把"有日期"当成"更晚"或"更可信"的理由。
6. 如果问题是"几次/多少个"这类计数，只数同一次事件时间线上的记录；
   同一件事的补记不算新增。
```

## 3. 剩余误差（不是契约能修的）

v4 剩 2 道 ❌（场景 3 换工作次数、场景 11 公司）与 1 道退步，全部因为 **top-4 混进了别的场景的记录**：

- 记录本身**没有场景/时间线标签**，契约只能靠日期判断，而跨场景记录恰好日期更晚
- 修它要动检索层：给记录加"场景/时间线"元数据，或在 top-4 里做同主题去重

## 4. 交付方式

契约必须进入**读者模型的系统提示**才生效。provider 只能返回检索结果，无法注入提示词。

**定稿方案（唯一推荐）：随包交付的 prompt-section 插件**，实现细节见 §4.1。下面是当初评估过的通道与结论，**不要按旧方案施工**：

| 通道 | 结论 |
|---|---|
| **prompt-section 插件（采用）** | `ctx.systemPrompt.section({name, order, text})`，普通插件即可追加；契约文本随仓库走；不碰 persona/preset |
| persona 按 id 打补丁（**已废弃**） | persona 在 preset 的 `config.plugins` 里、preset 非 group，patch 会 `entry not found` **静默不生效** |
| 整段重写 `preset-standard` | 需重抄整个 plugins 表，上游一变就漂，不采用 |
| skill（可选补充） | 写进 `~/.dsh/skills/`，靠模型按需加载；不保证加载，只作补充 |
| 结果 content 附带规则（备选） | 不依赖宿主，但模型可能把规则当数据/注入，效果未验证，不推荐 |
| 改宿主 `system-prompt.personaPrefix` | 会被各 preset 的 persona 段 shadow，实际无效 |

**装载方式（按源码核实）：手改 profile `package.json` 的 `dsh.profile.bundles` 数组加一行包名**。不要用 `install_bundle`：它会把 junction 变成 `file:` 依赖并重排 node_modules，且回滚 `remove_bundle` 会连带断掉 mnemon 的 provider 挂载。手改数组不跑 pnpm，junction 原样保留，回滚=删行+重启。

### 4.1 实现方式（已按源码核实，`docs/13` 有出处）

**❌ 不要按 `- id: persona` 打补丁**：persona 位于 preset 行的 `config.plugins` 里，而 preset 不是 `group:true` 的行，patch 的递归索引只进 group → 会 `entry not found` 被 warn+skip，**静默不生效**。（本文件早期版本写过这个错误方案，已废弃。）

**✅ 采用：随包交付的 prompt-section 插件**

- 本包 `plugin/` 增加 `package.json` 的 `dsh.bundle.patch`，并在包里提供一个 `./contract` 子路径插件：

  ```ts
  // plugin/src/contract-plugin.ts（对外子路径 ./contract → dist/contract-plugin.js）
  export const inject = ['systemPrompt']
  export function apply(ctx) {
    ctx.systemPrompt.section({ name: 'mnemon:reader-contract', order: 10250, text: CONTRACT })
  }
  ```

- 契约正文**单一来源**：`plugin/contracts/reader-contract-v4.zh.txt`。`plugin/src/contract-text.ts` 在运行时从包根读取该文件并导出 `READER_CONTRACT_V4`（构建产物 `dist/contract-text.js` 用 `../contracts/...` 定位，同样指向包根；`package.json` 的 `files` 含 `contracts`，npm 打包后仍可用）；测试断言「txt 文件 == 导出常量 == 本文 §2 代码块」逐字一致。**评测侧尚未接入**：`research/recall/reader_contract_eval.py` 仍内嵌 v4 正文（`CONTRACT_V4`），跨端共用同一文件是下一步（见 `docs/13` §3）；在接入之前改契约必须两边一起改。
- 实现文件名：插件是 `plugin/src/contract-plugin.ts`，**不是** `contract.ts`——后者已经是 provider 契约的类型镜像（5 个 src 模块引用），改名会牵连整包；对外子路径仍是 `./contract`，装载不受影响。`package.json` 的 `exports` 加 `./contract`、`files` 加 `cordis.patch.yml` 与 `contracts`、`dsh.bundle.patch` 指向 `./cordis.patch.yml`。
- bundle patch 只插这一条 prompt-section 行，**不碰 persona、不碰 preset**，因此不受 DSH 升级改写 preset 的影响。
- 已知限制：`minimal` preset 设了 `complete:true`，会吞掉追加段；`standard` / `cordis` / `ptc` 正常。
- 备选（A 不可行时）：仓库里另建 `bundle/` 小包，provider 保持现状。

### 4.2 改前改后检查清单

1. 备份 profile 的 `package.json`（`dsh.profile.bundles` 数组就是回滚点）。
2. 把包名加进 `dsh.profile.bundles` 后重启后端（不需要 `pnpm` / `install_bundle`）；新会话里确认系统提示出现 `mnemon:reader-contract` 段。
3. 回滚＝从 `dsh.profile.bundles` 删掉该行并重启；不动 mnemon 的 provider 挂载配置。
4. 验证：问"我车位在哪"（有换车位记录，应按最新日期答）；问血型类问题（应列出两种说法并反问）。

## 5. 维护规则

1. 契约变更 = 契约版本号 +1，并重跑 A–E 对照；不重跑的改动不算数。
2. 单条规则的效果必须有配对数据支撑（这次 v2→v3→v4 的每一步都有）。
3. 契约只约束"怎么读"，不改写入路径、不改检索排序。
4. 新增规则前先问：它修的是"读者行为"还是"检索/元数据"？后者不该写进契约（这次 2 道剩余 ❌ 就是例子）。
