# 06 · 对接层设计（第三层，v3）

> v3 修订：按终审改 3 处阻塞——**session_id 改从 `body.provider.settings.memoryBodyId` 取**（discover 把同值写进 connection，两台机器天然一致，不靠人工约定）；**discover 的 externalId 改取 shim 固定值/常量**（消除循环依赖）；**/health 必须 O(1) + 重建期不静默返回部分结果**。
>
> v2 修订：按第一轮评审改 5 处——装配形状（defineMemorySpaceProvider/host.install）、capabilities 全量键名、密钥获取路径、session_id 取值、fields scope 与 discover 形状。
>
> 依据：`05-provider接口契约.md`（源码核实，file:line）、`03-对接层契约映射.md`、`02-检索层设计.md` **v9（当前）**。

## 0. 一句话

**第三层是一个极薄的 TypeScript 适配器包**：实现 mnemon 的 `MemorySpaceProviderAdapter`，把每个方法翻译成对 shim 的一次 HTTP 调用，并在翻译时补齐契约要求的形状（回执 action、ISO 时间、results 数组、scoreSemantics）。业务逻辑一律不在这一层。

## 1. 装配形状（B1，照官方 honcho 模式）

子模块 **default export** 一个 `defineMemorySpaceProvider({ id, apply })` 的 typed child module；`apply(ctx, host, config)` 内部必须调 `host.install(ctx, { manifest, create })`，漏 install 会直接抛 "did not install a definition"（P:4280-4296、PJ:161）。

```ts
export default defineMemorySpaceProvider({
  id: 'factlayer',
  apply(ctx, host, config) {
    host.install(ctx, { manifest, create: (installCtx) => createProvider(installCtx, config) });
  },
});
```

硬约束：

- **`adapter.id === manifest.typeId`**（PJ:259）——两处必须逐字一致。
- `manifest.typeId` 必须等于 module 的 `id`（06 v1 漏写，05 §6.1 已列）。
- 本包落地方式：**首选随 `dsh-mnemon` 的 bundle patch（`cordis.patch.yml`）内置**，用户零手改（官方 9 个 provider 同款路径）；GUI 安装器只认 `dsh-mnemon-source-*` / `dsh-mnemon-strategy-*`（M:17131），**不要**为此改名（那是语义撒谎）。

## 2. 能力声明（B2：键名与全量布尔）

```ts
capabilities: {
  search: true,
  browse: false,
  graph: false,
  entities: false,
  related: false,
  remember: true,
  link: false,
  forget: false,
},
writeMode: 'exact',
deletionMode: 'unsupported',
scoreSemantics: 'provider-native',   // manifest 与 adapter 两处都写且一致
```

- 8 个布尔必须**写全**，不要只写用到的；漏写的键会被逐项校验拒绝（PC:115）。
- `deletionMode` 不是 `deletion`（v1 写错）；只追加 → `'unsupported'`，`forget` 不实现。
- 三处 `scoreSemantics` 语义：manifest 三值 / adapter 两值，**manifest 写 normalized 而 adapter 未声明会装配失败**。

## 3. 方法与字段映射（B5：discover 形状 + fields scope）

| 契约方法 | shim 调用 | 适配要点 |
|---|---|---|
| `discover()` | `GET /spaces` | **externalId 取 shim 返回的固定值**（或常量 `factlayer-default`），**不依赖 memory 字段**（保存配置时 memory 字段还不存在，取它就是循环依赖）。返回 `connection: { memoryBodyId: <同一个值> }`（该键已在 `fields[scope=memory]` 声明，合法）；**`externalId` 不变则重复调用幂等**（保留 active/name）。shim 不可达 → **抛错**，让保存失败有明确文案，不返回空数组 |
| `status()` | `GET /health` | 映射 `ProviderSpaceStatus`；**单独 2–3s 超时**（Source 每次目录刷新都调、且无超时，P:1992-2032）；超时返回 `{healthy:false, error:"starting/rebuilding"}`；**保留最近一次成功结果 ~30s 做 stale-while-revalidate**，并发调用合并成一次请求；漏实现 → 空间永远 unhealthy |
| `search(body, request)` | `POST /search` | `{items}` → **`{results}`**；`recorded_at(ms)` → `createdAt` ISO；剥掉事实层私有字段；`hint` 仅空结果透传且 `NO_MATCH` 开头（多空间拼接时每空间 hint 各自带前缀） |
| `remember(request)` | `POST /memories` | 见 §4 |
| `list(request)` | 空数组或 query 命中 | `browse:false` 下不伪造浏览能力；契约 `MemoryListRequest` 无 session/offset |
| `graph()` | 无 | 返回空 `MemoryGraphSnapshot`（能力位 false） |
| `get/related/link/forget/rememberMany/entityIndex/metadataSample` | 不实现 | 全部可选；`metadataSample` 若实现必须有 try/catch，否则 search 抛错会冒成 RPC internal |

**fields**（scope 决定取值路径）：

| key | scope | secret | 说明 |
|---|---|---|---|
| `baseUrl` | service | 否 | shim 地址 |
| `apiKey` | service | **是** | 可为空（仅回环时） |
| `memoryBodyId` | **memory** | 否 | 用户填的**固定空间标识**；discover 的 externalId 与 session_id 都用它 |

## 4. 密钥与配置的获取路径（B3：v1 完全漏掉）

契约不把 secret 值交给 `body.provider.settings`——那里只有 memory-scope 非 secret 值 + `configuredSecrets` 名单（无值）。**取值必须**：

```ts
const conn = await context.memorySpaces.providerConnection(spaceId, providerId); // PS.js:58-61
const baseUrl = conn.baseUrl;   // service scope
const apiKey = conn.apiKey;     // secret，可能为空
```

- `providerConnection` 自带 provider 身份校验，**不要**自己从 ctx 里翻凭据。
- **缓存按 `spaceId` 分键**，并在 `invalidateStatus` / `dispose` 时清掉——否则用户改了 key 仍用旧值。
- 配置缺失时：`status()` 返回 unhealthy 并带人话原因；`search/remember` 抛明确错误（不要静默空数组）。

## 5. 写入回执与三必填字段（B4 + 05 §4.4）

回执翻译（契约里最阴的一处）：

```json
{ "action": "stored", "committed": true, "count": 1,
  "memoryBodyIds": ["<space id>"], "ids": ["<memory id>"] }
```

- `action:"stored"` 命中 16 词白名单；`committed:true` 命中判定链第 6 步；两者并存无层拒绝（已核验）。
- **回执绝不能带 `memoryReceipt` 或 `completion` 键**：Host 对这两个键有更严的**结构化通道**——必须 `completion==="committed"` **且** `status==="succeeded"` **且** `committedAt` 可被 `Date.parse`，不满足直接判未落地；一旦出现，`committed:true` 的宽松启发式就失效了，反而更容易被判"没落地"。当前适配器输出上面的扁平回执（无这两个键），**保持现状**（`docs/21` §3.4 末尾；`M:7895-7900`）。
- `client_write_id` 每次 uuid4 → **shim 的 duplicated 分支永远不会命中**，故**不实现"幂等回执"分支**（终审指出的自相矛盾）；若将来加 outbox 重试，再启用。
- shim 真实失败 → 抛错（写路径无重试，冒成 RPC internal）。
- **超时错误文案必须写"结果未知，可能已写入"**——shim 可能已落盘，模型若当成"失败"会重写产生重复。

三必填字段来源：

| 字段 | 取值 | 理由 |
|---|---|---|
| `source_client` | `"mnemon-provider"` | 标记来源 |
| `session_id` | **`body.provider.settings.memoryBodyId`**（memory scope 非密字段，remember 回调里可读） | 该值由 discover 写入 `connection`、来自 shim 固定值，**两台机器天然一致**，不靠 README 人工约定；**缺值直接抛错**，不得用 `body.id` 或默认值静默兜底 |
| `client_write_id` | 每次 uuid4 | 契约无幂等位；内容摘要会合并"真的写了两遍"（违反"绝不静默丢"）；上游无重试，重复概率低，**宁可重复也不吞** |

- **shim 侧约束**：`/search` **不按 `session_id` 过滤**（否则两台机器不同值会造成"A 写的 B 搜不到"的无声分裂）；`session_id` 只用于写入分组与会话展开。

## 6. 检索结果字段映射（05 §7.2）

| shim 字段 | 契约落点 | 处理 |
|---|---|---|
| `id` | `Insight.id` | 直传；缺失/空/超 1000 → 适配器**抛错**（比静默丢安全） |
| `content` | `Insight.content` | 直传（已 1200 截断带自报）；写侧注意 Source 上限 8192 |
| `recorded_at`(ms) | `createdAt` | **转 ISO 8601 UTC**；Source 只透传不校验格式（`docs/21` §5），但下游按字符串排序/展示，必须给 ISO；**逐条 guard**：None/负数/NaN/超范围 → 省略该字段并加 `tags:["no-time"]`（排序退化但该条仍在结果里），**绝不因单条坏记录让整个空间 unavailable**，也不编造兜底时间 |
| `score` | `Insight.score` | 保留数值；**shim 未给时补默认值**（缺 score → tier unknown → 策略每回合只收 1 条） |
| `tags` | `Insight.tags` | 保留；无逗号、≤8 个、每个 ≤300 |
| `seq`/`session_id`/`routes`/`content_truncated`/`expanded*`/`inherited_rank` | — | **剥掉**（策略层白名单也会丢，留着浪费 payload） |

## 7. 失败与降级

- 读：shim 5xx/超时 → 抛错，Source 逐空间降级 `unavailable` + hint；**不得返回空数组冒充"没有记忆"**。
- 写：抛错，不吞；超时文案见 §5。
- 超时：search 15s（对齐官方基类）、**status 2–3s**、remember 15s。shim 内 R1 已 3s 超时+熔断，两层不放大（status 短超时避免拖住 Memory 页）。
- `hint`：仅空结果有意义；多空间时每空间 hint 各自以 `NO_MATCH` 开头。

### 7.1 shim 侧 `/health` 与重建（终审阻塞 3）

- **`/health` 必须 O(1)**：只读存活标记与状态位，**不触发重建、不加锁、不扫表**。重建在后台跑，`/health` 报 `rebuilding: true`。
- **重建期间不得静默返回部分结果**：`/search`、`/memories` 在重建中要么返回明确 `503 rebuilding`，要么按"旧索引完整可用"语义继续服务——**不允许"只搜到一半"**。适配器侧收到 503 → 抛明确错误（"索引重建中，请稍后"），不当成空结果。
- 适配器 status：2–3s 超时 → `{healthy:false, error:"starting/rebuilding"}`；**stale-while-revalidate ~30s**；并发 status 调用合并。
- 理由：迁移/重建会让 `/health` 变慢；若 status 每次目录刷新都超时，空间会反复显示不健康，违反"零人工维护"。

## 8. manifest 易错清单

- `apiVersion` 固定串（照抄同版本官方 provider）。
- `typeId === module.id === adapter.id`（三处一致）。
- `secrets` 必须与 `fields` 中 `secret:true` 的集合**完全一致**。
- `scoreSemantics` 两处声明一致。
- `externalId` ≤2000 字符且重复时抛错。
- 写侧 content 上限 8192（05），RPC 100k 与 Source 8192 不一致——验收要加长内容用例。

## 9. 端到端验收

1. `discover()` 连点两次不重复挂载（幂等）。
2. `remember` → 工具结果 `action` **不是** `unknown`、`memoryBodyIds` 非空、空间被激活。
3. `search` 命中 → `createdAt` 可读、score 数值存在、私有字段不出现。
4. 空结果 → 模型看到 `unavailable` 且以 `NO_MATCH` 开头。
5. shim 停机 → search 降级 unavailable、remember 抛错 internal，**不静默空**。
6. 超时 → 错误文案含"结果未知，可能已写入"。
7. 长 content（>8192）→ 明确报错，不截断不静默。
8. payload 只含契约字段（单测断言）。
9. **坏时间戳**：`recorded_at` 非法 → 省略 `createdAt` 并加 `tags:["no-time"]`，该条**仍出现在 results 里**（不因排序退化被丢）。
10. **重建期**：`/health` 在重建中仍 O(1) 返回且 `rebuilding:true`；`/search` 返回 503 而非部分结果；适配器抛明确错误。
11. **实测一次"写入抛错不自动重试"**：shim 故意 500，确认上游不会自动重发（契约称无重试，运行期未测）。

## 10. 待决问题

1. **会话粒度**：`session_id` = 用户固定 `memoryBodyId`，跨机一致但粒度粗（一个空间 = 一个"会话"）。若要真正的多会话，需要 discover 返回多空间或扩展契约——短期不做。
2. **`list` 深度**：`browse:false` 时返回空；若 GUI 依赖 list 展示，再补最小实现。
3. **分发**：首选 bundle patch 内置；是否向上游提交（需 `dsh-mnemon-source-*` 命名，语义不准）暂不做。
