### 1.2 `@deepseek-ai/dsh-system-prompt`：普通插件可以"追加"，不必覆盖 persona

**包位置与导出**

- 包：`packages/core/system-prompt`，`package.json` 里 `"name": "@deepseek-ai/dsh-system-prompt"`、`"version": "0.2.2-rc.2"`，`exports` 暴露 `"."`、`"./src/*"`、`"./package.json"`。
- 服务挂载在 `ctx.systemPrompt`（`packages/core/system-prompt/src/index.ts:13-16`，服务类 `:436-475`）。
- README 明确："Mount `dsh-system-prompt` wherever agents run: it provides `ctx.systemPrompt`, the registry every prompt contribution lands in."（`packages/core/system-prompt/README.md:28`）

**注册 API（本任务要的那一个）**

| API | 签名/语义 | 证据 |
|---|---|---|
| `section(section)` | 注册有序提示词段；`name` 在同一作用域内唯一，重复注册抛错；`order` 必须有限，非有限抛错；返回 disposer | `src/index.ts:485-494`；`PromptSection` 定义 `:53-76` |
| `getSectionOrder(name)` / `getContextOrder(name)` | 取"仓库中心分配"的排序位；外部贡献也可直接用任意有限 order | `src/index.ts:501-512`；README:56 |
| `context(ctx)` | 注册动态运行时上下文（进 user-role 快照，不进 system prompt） | `src/index.ts:520-529` |
| `variable(name, fn)` | 注册 `{{name}}` 变量 | `src/index.ts:568-577` |
| `suppressRuntimeContext()` | 关闭可选运行时上下文 | `src/index.ts:537-543` |
| `assemble()` / `refreshContext()` | 每步装配 / 请求准入刷新 | `src/index.ts:621-696`、`:589-609` |

已分配 section 顺序见 `src/index.ts:136-173`：`HARNESS_IDENTITY=-1000`、`DEPLOYMENT_PERSONA_PREFIX=0`、工具提示 1000–5000、`HARNESS_SOURCE=10000`、`WEB_SURFACE=10100`、`DEPLOYMENT_PERSONA_SUFFIX=10200`。
persona 段的名字是导出的常量：`PERSONA_PREFIX_SECTION='deployment:persona-prefix'`、`PERSONA_SUFFIX_SECTION='deployment:persona-suffix'`（`src/index.ts:197-200`）。

**示例调用（普通插件，追加一段，不动 persona）**

```ts
// plugin/src/contract-plugin.ts
// 运行时只需要宿主已提供 ctx.systemPrompt；不要把它写成 @deepseek-ai/dsh-* 的 peerDependency（会进兼容检查）。
interface PromptApi {
  section(s: { name: string; order: number; text: string }): () => void
}
interface Ctx { systemPrompt: PromptApi }

export const name = 'mnemon-reader-contract'
export const inject = ['systemPrompt']

export function apply(ctx: Ctx): void {
  ctx.systemPrompt.section({
    name: 'mnemon:reader-contract',   // 全局唯一；与 persona 段不同名 → 并存而非覆盖
    order: 10250,                     // 10200 persona suffix 之后；外部贡献允许任意有限 order
    text: READER_CONTRACT_V4,
  })
}
```

**边界（都是源码/文档里写明的）**

- 同名同作用域重复注册直接抛错（`src/index.ts:485-493`；`PromptLayer` 的重复名错误在 `:414-422`）。
- 作用域内的段会 shadow 同名的全局段；全局段对所有 agent 都参与装配（`src/index.ts:638` 的 `merge(scope, ...)`，测试 `tests/scoped.spec.ts:69-73`）。
- `complete: true` 的段会**吞掉**所有其它段：装配后在 `:688-695` 用该段替换整个 sections。shipped preset 里 **`minimal` 开了 `complete: true`**（`packages/bundle/web-app/presets/minimal.patch.yml:11-16`，`complete` 在 `:15`，且 `includeRuntimeContext: false`），所以 minimal 会话里契约段会被吞掉；`standard`/`cordis`/`ptc` 没开（三份文件里 `complete:` 只出现在 plan-mode 的 `section` 文本里）。
- **没有"配置里写一段提示词"的通用插件**：README 的限制条款写着 "Deployment-authored prompt text is config/composition only … there is no end-user prompt-editing API."（`README.md:179`）。所以必须有一个插件（或改一个有 `section` 配置的插件），不能只改一个字符串配置。

### 1.3 `@deepseek-ai/dsh-persona` 的 schema，以及"按 id 打补丁"到底改了什么

**schema（4 个字段，不是只有 prefix）** — `packages/preset/persona/src/index.ts:30-54`

| 字段 | 类型/默认 | 作用 |
|---|---|---|
| `prefix` | string，**required** | 渲染成 `deployment:persona-prefix` 段（order 0） |
| `suffix` | string，默认 `''` | 渲染成 `deployment:persona-suffix` 段（order 10200）；省略/空会**遮蔽掉**全局 suffix，不继承 |
| `complete` | boolean，默认 `false` | 只用 prefix 作为完整系统提示，压掉其它所有段 |
| `includeRuntimeContext` | boolean，默认 `true` | false 时调用 `suppressRuntimeContext()`，关闭该 agent 的可选运行时上下文 |

**它是 scope-only 的**：`src/index.ts:1-13` 的模块注释写明"mounted globally it collides with the registry's own registration and fails loud"；README:12/28 同样说明。也就是说，**不能在 profile 顶层直接挂一个 persona 行**——`system-prompt` 服务自己在全局注册了同名 `deployment:persona-prefix`，会因重名失败。

**patch 的真实语义** — `vendor/include/src/patch.ts:47-109`

1. 非 insert 的 patch 必须有 `id`（`:86-89`）；按 id 在**已合成的顶层条目表**里找目标（`:51-60`）。
2. 找不到目标：`warn('patch: entry %C not found')` 然后 **跳过**（`:91-95`）。
3. 命中后是**逐字段赋值**：`target[key] = value`（`:102-105`）。所以 `config` 是**整块替换**，不是深合并——必须把该行需要的字段全部重写（同一结论见 dsh-doc 的 `references/composition-reference.md:10-11`）。
4. 只有 `group: true` 且 `config` 是数组的行才会被递归索引（`:51-60` 的 `buildMap`、`:407` 的 `ensureIds`）。**preset 不是 group**：`preset-standard` 行的 `config` 是对象（`{id, order, plugins}`），plugins 在 `config.plugins` 里，见 `packages/bundle/web-app/presets/standard.patch.yml:5-17`。

**因此，针对"只改 persona config"这个问题，答案分三层：**

- 如果目标是**行级**：`- id: X config: {...}` 确实只替换 X 这一行的 config，其它行不动。✅
- 但 **`persona` 不是 profile 顶层的行**：它只存在于 preset 声明行的 `config.plugins` 里（上引 `standard.patch.yml:11-15`），而 preset 行不是 group。当前 profile 的 `cordis.patch.yml`（`C:\Users\ZhaoY\.dsh\profiles\web\cordis.patch.yml`）通篇没有 `persona` 行，只有宿主行（`webserver`、`connection`、`mnemon`、`mnemon-source-memory-spaces` 等）。在当前 profile 写 `- id: persona` 会得到 `patch: entry "persona" not found` 并被跳过——**doc 12 §4.1 的样例按现状不生效**。❌
- 改 preset 里的 persona 只有一条真路：**`- id: preset-standard` 全量重写 `config`**（含整个 plugins 表）。这只影响该 preset 行，但等于把整个 preset 复制进 profile；上游 preset 一变就要重抄。preset registry 的文档也确认 override 是"keyed by that row's id"（`packages/preset/agent-preset-registry/README.md:48`），且"a user override replaces the …"（同文件 `:99`）。⚠️
- 另一条看似可行的路——改宿主 `system-prompt` 行的 `personaPrefix`——**对 preset 会话无效**：所有 shipped preset 都自带 persona 行（`standard.patch.yml:11`），作用域段会 shadow 全局段（`README.md:56`、`src/index.ts:638`）。宿主行的值只在没有 preset persona 的 agent 上生效。❌

补充：doc 12 的样例还漏了 `suffix/complete/includeRuntimeContext`——如果哪天真去 patch persona 行，`config` 整块替换会把 `includeRuntimeContext` 从默认 true 变成"未声明"，schema 会补默认值，但语义上要显式写全（README 的示例只写了 prefix，因为它是新增行，不是覆盖）。

### 1.4 一个包能否同时是 provider 和 bundle？

**bundle 的 package.json 约定**（`references/host-plugin.md:3-27` 是文档，源码在下面）

- 判据就一句：`package.json` 里有 `dsh.bundle.patch`（字符串或字符串数组）；见 `packages/boot/app-boot/src/profile.ts:55-63`（`bundlePatchFiles`）、`:69-75`（`bundlePatchPaths`）。
- 可选 `dsh.bundle.platforms`（平台白名单，`packages/boot/app-boot/src/bundle-platform.ts`）、`dsh.bundle.listedByDefault`（Plugin Manager 是否默认列出）。
- bundle 包本身**不会**被当作插件挂载：它只贡献 patch 行。`profile.ts:695` 对 `dsh.profile.bundles` 里的名字要求必须有 `dsh.bundle`，否则整个 bundle 被 `skippedBundles` 跳过。
- 解析顺序：安装目录优先、profile 其次（`profile.ts:629-662` 的 `resolveBundleDir`）。

**`plugin_manager.install_bundle` 的行为**（`packages/boot/plugin-manager/src/operations.ts`）

1. 安装前预检：对要装的 spec 读 manifest（本地目录直接读 `package.json`），跑 `evaluatePluginCompatibility`（`:363-380`）。
2. 兼容规则：**`engines.dsh` 优先；否则只检查 `@deepseek-ai/dsh` / `@deepseek-ai/dsh-*` 的 peer**；其它 peer（cordis、dsh-mnemon…）一律忽略（`packages/boot/app-boot/src/plugin-compatibility.ts:55-74`）。本包 peer 是 `@deepseek-ai/cordis`、`dsh-mnemon`、`dsh-mnemon-source-memory-spaces`，**不会**触发兼容拒绝；`engines` 只有 `node`。
3. 执行 pnpm add；失败/不满足 `expected` 会回滚 profile 的 `package.json`/lock（`operations.ts` 里的 `savedFiles` 与 `restore()`）。
4. 安装后 reconcile：新依赖若声明了 `dsh.bundle`，加载其每个 patch 校验、并**自动加入 `dsh.profile.bundles`**（`:96-135`，`bundles.push` 在 `:120`）；没声明 `dsh.bundle` 的新依赖只警告"installed as a plain dependency, not a profile layer"（`:110`）。
5. 已是 bundle 的同名包再装会报 `already-installed`（`src/tools.ts:18`），要先 `remove_bundle`。安装会执行包里的代码，需要 Full access 或审批；本次没有执行任何安装。

**能否一个包两用**：能。`use: dsh-mnemon-provider-factlayer` 是普通包导入；bundle 只看 manifest + patch。两者互不干扰。需要同时满足：
- 包名不变（mnemon 配置里的 `use:` 不改）；
- `exports["."]` 仍是 provider（`plugin/package.json` 现状），**新增** `./contract` 子路径导出插件模块；
- `files` 加 `dist`、`cordis.patch.yml`、`contracts/`；
- 不要为了类型检查把 `@deepseek-ai/dsh-system-prompt` 写进 `peerDependencies`——那会因 `@deepseek-ai/dsh-*` 前缀进入兼容检查（`plugin-compatibility.ts:69`）。用结构化类型（§1.2 示例）或只放 devDependency。

**当前环境特有的坑（未验证）**：本机的 provider 是 **junction**（`profile/node_modules/dsh-mnemon-provider-factlayer → E:\dsh-mnemon-provider-graphiti\plugin`），且没有写进 profile 的 `package.json` 依赖。`install_bundle` 会 `pnpm add <本地目录>` 把它变成 `file:`/`link:` 依赖，可能替换掉 junction 的链接方式。**这一步没有实际执行，行为未验证**——第一次安装应在可回滚的 profile 上做，或先备份 `package.json`/`pnpm-lock.yaml`。

### 1.5 结论与落地布局（推荐：bundle + 全局 section 插件）

**为什么不是 persona**：persona 只能挂在 preset 里，改它必须整表重写 preset 或新建 preset；契约文本和 preset 生命周期绑在一起，上游一升级就漂。prompt section 是**公开扩展点**，不依赖 preset，也不碰人格设定。

**推荐布局（"契约随包走"：一个包，provider + bundle）**

```text
plugin/
├─ package.json                 # 加 dsh.bundle.patch；exports 加 "./contract"；files 加 dist、cordis.patch.yml、contracts/
├─ cordis.patch.yml             # 新增：一条 insert
├─ contracts/
│  └─ reader-contract-v4.zh.txt # 唯一正文来源（逐字抄 docs/12 §2 的代码块）
├─ src/
│  ├─ contract-text.ts          # 内嵌同一段文字 + READER_CONTRACT_VERSION='v4'（运行时读文件会多一个失败点，内嵌更稳）
│  ├─ contract-plugin.ts        # 上面 §1.2 的 apply/inject
│  └─ index.ts                  # 不动：仍是 provider 的 default export
└─ tests/
   └─ contract.test.ts          # 断言：contract-text.ts == contracts/*.txt == docs/12 §2 代码块
```

`package.json` 增量（示意）：

```json
{
  "exports": {
    ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" },
    "./contract": { "types": "./dist/contract-plugin.d.ts", "default": "./dist/contract-plugin.js" },
    "./manifest": { "types": "./dist/manifest.d.ts", "default": "./dist/manifest.js" },
    "./package.json": "./package.json"
  },
  "files": ["dist", "README.md", "cordis.patch.yml", "contracts"],
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}
```

`cordis.patch.yml`（**不要真的装，这是片段**）：

```yaml
# 本包作为 profile bundle 时应用的层；只插入一条 Host 行。
# 行名指向包内子路径导出，不引用包主入口（主入口是 provider）。
- insert:
    - id: mnemon-reader-contract
      name: dsh-mnemon-provider-factlayer/contract
      # 可选：config 留空；插件本身不带 Config schema
```

生效链路：boot 时 `loadProfileDirectory` 解析本包 → 校验兼容 → 读 `cordis.patch.yml` → 合成顶层条目（`profile.ts:678-707`、`:755-762`）→ 挂载 Host 行 → 插件 `inject:['systemPrompt']` → 注册全局段 → 每个 agent 每步 `assemble()` 带上这一段。

**代价与边界**
- 全局段对同一 Host 进程内的所有 agent 生效（含 subagent 子会话）；每轮多 ~0.4–0.7K 字符（v4 正文约 600 字）。契约首句是"回答关于我本人记忆的问题时…"，对普通编码会话影响小。
- 开了 `complete: true` 的 persona 会屏蔽该段（见 §1.2 边界）。shipped preset 里只有 `minimal` 这么配；`standard`/`cordis`/`ptc` 正常。
- 想更窄的作用域：把同一插件行插进某个 preset 的 `plugins`（作用域注册，只在那个 preset 的 agent 生效）——但那就又回到"改 preset"了，只建议给"评测专用读者会话"用。

**回滚**：`remove_bundle`（或把该行 `disabled: true` 的 profile patch），无需动任何既有配置。

> 注意：`research/recall/reader_eval.py` / `reader_contract_eval.py` 的读者是**外部 API 调用**，prompt 在 Python 里自己拼（`reader_eval.py:140-147`、`reader_contract_eval.py:387`）。DSH 系统提示的改动**不会**影响那套评测；两边唯一的共同点应是我们抽出来的契约文本文件。所以"进系统提示"只解决生产侧读者，"评测侧注入"要单独改 Python（或直接读同一份 `contracts/reader-contract-v4.zh.txt`）。

> 建议把 doc 12 §4 的通道表替换为指向本文 §1.5（doc 12 是定稿，这次没有改它）。

**备选（若不想动 provider 包的装包身份）**：仓库里另建 `bundle/` 小包，只含契约文本 + 插件 + patch；`install_bundle` 装它即可，provider 保持 junction 现状。代价是多一个包，但安装面最干净。

### 1.6 未验证 / 风险清单

1. `install_bundle` 对"同名包已以 junction 存在"的行为（是否替换链接、是否需要先 `remove_bundle`）**未验证**。
2. 打包（`files`）后 `contracts/` 与 `dist/contract-plugin.js` 是否完整进包 **未验证**（本地目录安装不读 `files`，发布/打包才暴露）。
3. 真实装配后的最终系统提示没有实测（本任务只读）；`complete` persona 吞段、作用域 shadow 都是从源码读出的结论。
4. 本会话能看到 persona 原文偏向 `cordis` preset（"You help the user customize DeepSeek Harness itself."），但**没有**逐一核对每个 preset 的实际选择。
5. `patch` 对 `config` 是整块替换这一点，源码明确；但"profile patch 能否命中 preset 里的 persona"只在当前 profile（无顶层 persona 行）上从代码推断，未在运行实例上实测警告文本。

### 2.1 总表

| 基准 | 公开数据/链接 | 规模 | 格式（关键字段） | License | 能否转成 query+候选记录+gold 证据 | 主要预处理 | 答案泄漏风险 |

### 2.2 逐项要点

**LongMemEval** — 已经实测下载 `longmemeval_oracle.json`（15.4MB）核对：
- 500 条、字段与 README 一致；类型分布：`temporal-reasoning 133`、`multi-session 133`、`knowledge-update 78`、`single-session-preference 30`、`single-session-assistant 56`、`single-session-user 70`；`_abs` 后缀（abstention）**30 条**。
- 每题的证据会话显式：`answer_session_ids` + 会话内 `has_answer: true` 轮次（全量 896 个）。这正是我们要的"gold 证据"。
- 注意：`oracle` 版每题只给证据会话（示例是 3 个），所以它测的是**读者**不是检索；要测检索用 `_s`/`_m`。每题**独立语料**，不能拼成一个大库。
- 评测脚本用 GPT-4o 做 LLM judge（README 的 `src/evaluation/evaluate_qa.py`）。

**MemoryAgentBench** — 论文 Table 1 写明 #Q=2071、context 103k–1.44M；README 的指标表说明：AR（event_qa/ruler）、CR（factconsolidation）用 `substring_exact_match`，LRU（detectiveQA）用 `exact_match`，TTL（ICL 系列）用 `exact_match`，只有内嵌的 LongMemEval 子任务用 LLM-as-judge。四个能力维度是 AR / TTL / LRU / **Selective Forgetting（README 目录名写成 Conflict Resolution）**——两套叫法并存，引用时注意。数据结构是"一次注入、多次提问"：一个 `context` 对应 `questions[]`，适合我们按上下文切记录后做 top-k。

**STALE** — 数据集卡片与字段已核对（`T1_T2_400_FULL.json` 是 JSON 顶层数组，首元素字段与卡片一致；用 Range 读了文件头）。三维探针：dim1 显式状态校验、dim2 抗陈旧前提、dim3 下游策略迁移；这三类都不是 v4 的"两条记录冲突"形态，而是**隐式失效**（后一条观察没有明确"换了/改成"）。这一点对契约评估很关键（§2.4）。

**Temporal Belief Reconstruction** — 先纠正任务里的假设：**它有公开数据**，不是只有论文。作者在 Zenodo 同时挂了两份：
- `20130103`（2026-05-12）只有 `paper.pdf`；
- `20234724`（2026-05）有 `scenarios.tsv`、`claims.tsv`、`croissant.json`、`agent-memory-audit-0.3.1-source-data.zip`（4.4MB，含 corpus/结果/测试）、`SHA256SUMS`。
- 论文摘要说 395 scenarios / 16 种系统配置；我数 `scenarios.tsv` 是 522 行（含 `.retroactive-visible` 这类子测试）——**两个口径的差异没有在论文里核对**，引用时写"论文 395，发布快照 522 行"。
- 它是"一致性测试"（conformance test），不是对话记忆：记录是双时态 claim（valid time / transaction time），查询带 `as_of_valid`/`as_of_txn`。

### 2.3 题量与调用估算（每题 1 次 reader + 1 次判分）

| 基准 | 题数 | reader | 判分 | 1+1 合计 |
|---|---:|---:|---:|---:|
| LongMemEval | 500 | 500 | 500（LLM judge 必需） | **1000** |
| MemoryAgentBench | 2071 | 2071 | ≤2071（只有内嵌 LME 子集需 judge，**未验证**） | **4142** |
| STALE | 1200 | 1200 | 0–1200（维度判定方式**未验证**，没找到公开判分脚本） | **2400** |
| TBR | 522 | 522 | 0（`expected_answer`/`expected_epistemic` 可精确匹配） | **1044** |
| **合计** | **4293** | **4293** | **500–4293** | **≈4800–8600** |

口径说明：
- 按题 1+1 的**上界是 8586 次调用**（4293×2）；只跑必需判分的**下界约 4800**（4293 reader + 500 judge）。实际落在两者之间，取决于 STALE 和 MAB 用 judge 还是规则判分。
- MAB 的 2071 来自论文 Table 1，不是逐题 count；按 split 的题数分布**未验证**。
- 不含预检/重试/多 seed；也不含 LME `_m` 变体（1.5M tokens/题）的额外成本。
- 这些都是**单 reader** 口径（每题只调一次模型、只喂 top-k 条记录）；项目现有 40 题库的 A–E 对照是 40 题 × 5 组（含判分共 400 次调用），量级差一个数量级。

### 2.4 与 v4 中文契约的错配（整合前必须决定）

1. **语言**：四个基准全是英文，v4 正文是中文。要么写英文版 v4（新版本号 + 重跑 A–E），要么在评测里用中文契约 + 英文题目——后者会引入语言混杂，不建议。
2. **冲突类型**：v4 第 2a 条只处理"日期不同 + 较晚记录明确写了改变（换了/改成/调到…）"。STALE 和 TBR 考的恰恰是**隐式失效**（没有显式否定词），按字面很可能落到 2b"列出两种说法并反问"——这不是基准要的"识别旧状态已失效"。要在这两个基准上得分，必须新增条款（=v5），不能指望 v4 直接迁移。
3. **对齐得上的部分**：LME 的 `knowledge-update` ↔ v4 2a；`temporal-reasoning` ↔ v4 1/5；abstention ↔ v4 3；`multi-session` 计数 ↔ v4 6。这部分可以先拿 LME 做回归。
4. **不该进契约评测的**：MAB 的 TTL（测试时学习）和 LRU（长文摘要/侦探 QA）不是"读多条记忆"的问题，放进契约 A/B 对照会稀释归因。
