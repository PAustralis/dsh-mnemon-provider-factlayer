## 1. 问题

`docs/08` 的生产失败分析里，sid 33 问的是「2025 年」，但 119 条语料中
「2025」只出现在 `raw_date` 字段：

| doc | raw_date | 正文 |
|---|---|---|
| 95 | `2025` | 体检查出血脂偏高，医生让我少吃油腻。 |
| 96 | `2026-03-20` | 复查了，血脂已经正常。 |
| 97 | `2026-11-05` | 今年体检尿酸偏高，又开始忌口。 |

v1 索引文本只有 content，向量路能看见“体检/血脂”，看不见“2025”，于是
被其他年代的体检记录挤到第 5–9 名，R@4=0。事实层本来就有 `event_time`，
缺的是把它**确定性**地放进派生索引。

## 2. 实现

### 2.1 索引文本（`app/index_text.py`，纯函数）

```
索引文本 = 日期前缀 + "\n" + content
```

前缀同时给 ISO 与中文自然形式：

| 事实层字段 | 索引前缀 |
|---|---|
| `event_time=2025`, precision=year | `2025 2025年` |
| `event_time=2025-03`, precision=month | `2025-03 2025年3月` |
| `event_time=2025-03-14`, precision=day/instant | `2025-03-14 2025年3月14日` |
| `event_time=NULL` | `recorded_at` 的 UTC 日期 + 中文形式（如 `2026-11-12 2026年11月12日`） |
| 两者都没有 | 无前缀，仅 content |

- 分隔符固定为 `"\n"`：不产 CJK/Latin token，日期尾字不会和正文首字粘成
  「年体」之类双字（单测断言）。
- 无时钟、无配置、无随机：同一记录的索引文本逐字节一致，重建结果与写入时一致。
- 非法 `event_time`（如 `2025-13`、`2025-02-30`、精度不符）**抛 ValueError**，
  不静默回退——派生失败必须显式暴露。
- `event_time` 为空串按无日期处理；`recorded_at` 缺失/非法时退化为无前缀。

### 2.2 三条派生路径共用同一构造函数

| 路径 | 改动 |
|---|---|
| 写入即索引（`write_path.create_memory`） | `memories_ngrams` / `memories_fts_bigram` / `memories_fts_trigram` 都用索引文本；同一事务 |
| 派生 `fts` stage（`derive.make_fts_processor`） | 同上，重复执行幂等 |
| 派生 `embedding` stage（`derive.make_embedding_processor`） | `provider.embed([index_text])`，不再只发 content |
| 全量重建（`derive.rebuild_all`） | 向量、ngram、trigram 全部用索引文本 |

**content 本身不动**：`memories.content`、`/search` 返回的 `content`、
`GET /memories/{id}` 的全文都是原文；前缀只存在于派生层。

### 2.3 版本化重建

- `INDEX_TEXT_VERSION=2` 写入 `meta.index_text_version`。
- 空库在 `init_db()` 直接写当前版本；有记录的库：
  - `rebuild_all()` 在同一写事务里写版本（成功才宣称升级）；
  - 启动时 `index_text_rebuild_needed()` 判断 `stored < current` 且有记录 →
    **lifespan 起后台线程**跑一次 `pipeline.rebuild_all()`，启动不等待；
  - 重建期间置 `RebuildGate`：`/search`、写入、`/admin/search` 明确 503，
    不返回半张索引；`/health` 仍可读。
- `/health.index_text_version` 暴露：
  `{current, stored, up_to_date, rebuild_needed, last_rebuild}`；
  失败时 `alerts` 含 `index_text_rebuild_failed` 与
  `index_text_version_stale: 1 < 2`。
- 失败**显式报错**：ERROR 日志 + `index_text_rebuild.status=failed`，旧索引
  保留；下次启动/`/admin/rebuild` 可重试，绝不静默宣称成功。
- 一个容易错的边界：`rebuild_all(skip_embedding=True)`（迁移时无 provider）
  会保留旧向量。此时若直接写 v2，旧 content-only 向量会以 v2 名义继续被
  向量路使用。实现里**只有 `not skip_embedding` 或库内没有任何 embeddings 行
  时才写版本**；否则版本保持旧值，等有 provider 的完整重建再升级。

## 3. 评测设置

- 同一批 119 条语料 + 40 题；query 仍是题库【用户问】原文（只做 NFKC）。

  `write_path.create_memory`，再用 `DerivePipeline.rebuild_all()` 重建派生层；

### 4.4 sid 33 专项

```
问题：我 2025 年体检查出了什么问题?
gold：doc 95（raw_date=2025）、96（2026-03-20）、97（2026-11-05）

向量路 before：名次 [9, 6, 5]，R@4=0.000
向量路 after ：名次 [1, 8, 6]，R@4=0.333

```

doc 95 的正文没有“2025”，加前缀后索引文本以
`2025 2025年` 开头，向量路把它排到第 1。R@4 的 0.333 是 1/3（3 条 gold 中
命中 1 条）；doc 96、97 仍在 top-20 内（R@20=1.0 不变），只是名次轻微后移
（6→8、5→6），没有影响 R@6/R@20。

### 4.5 产品路径一致性

`index_text_eval.py` 不只用 numpy 直接排序，还：

1. 用 `write_path.create_memory` 真实入库（event_time 来自 raw_date）；
2. 用 `DerivePipeline.rebuild_all()` 重建派生层；
3. 用产品 `RetrievalService.vector_route()/bigram_route()` 排序。

结果与直接矩阵排序 **40 题 top-50 逐位一致**（vector/bigram 都是
`identical_top50=true, mismatch_count=0`），证明评测测的就是产品实际索引，
不是脚本自己另算的一套。

## 7. 约束核对

| 约束 | 落实 |
|---|---|
| 不引入可调参数 | 前缀格式、分隔符、版本号都是常量；无环境变量/配置项 |
| 不改事实层表结构 | 未改 `memories` schema；`content` 原样 |
| 不改写入路径判断逻辑 | 只改派生索引文本构造；幂等/409/校验逻辑未动 |
| 重建失败显式报错 | `rebuild_all` 抛错；后台任务 ERROR + meta failed + `/health` 告警 |
| 派生可弃可重建 | 所有前缀都在派生层；`rebuild_all()` 可重复、结果一致 |
| 版本不匹配不阻塞启动 | lifespan 起后台线程；`/health` 立即可读，重建期读写明确 503 |

## 9. 结论

日期前缀是一个**低成本、可解释、无 top-4 回归**的修复：

- 用事实层已有的 `event_time`（缺失时 `recorded_at` UTC 回退），不新增字段、
  不引入可调参数；
- 索引文本纯函数化，派生层可随时删掉重跑，版本号保证旧库启动时自动重建；
- sid 33 从第 9 名进入第 1 名，R@4 +0.0271（CI 不含 0），top-4 没有变差题；
- R@6/R@20 各 −0.0042，定位到 sid 3/25/35 的 5–20 名重排，属于日期信号
  对“年份不匹配”记录的正常降权，不是召回能力倒退；
- 二元组降级路 R@4 −0.0187，但主路径是向量单路，且 R@6/R@20 略升。

后续若要把 R@6/R@20 也拉正，可评估“只在查询含年份/月份时才给文档加日期”
之类的查询侧规则；但那会引入可调条件，本次按约束不做。
